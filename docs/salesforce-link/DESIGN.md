# Salesforce ↔ ERP: the design

Recommended 2026-09-14, after discovery (`DISCOVERY.md`) and a design panel: three
independent proposals — the ERP polling Salesforce, Salesforce pushing to the ERP,
and a thin scheduled mirror — each scored by three judges (a Salesforce admin, the
ERP engineer, the sampling incharge and a salesperson) on correctness, fit with what
exists, failure handling, smallest first ship and Salesforce realism. The thin
mirror scored highest (40.7 of 50); the ERP-as-middleware 38.7; Salesforce-pushes
37.7. No design had a fatal flaw; every judge named concrete gaps, and this
synthesis starts from the winner and closes them with the best of the other two.

Everything below is the panel's synthesis, verbatim under headings. The owner's
decisions are in `OPEN-QUESTIONS.md`; the build runs on the defaults there until he
says otherwise.

## The shape, in one paragraph

The ERP is the middleware. One Vercel cron, GET /api/salesforce/sync every 10 minutes, runs four phases — pull, check, stock, push — against a client-credentials Connected App; Salesforce never calls the ERP. (A) Every run aggregates AVAILABLE, whole, sales-approved slabs by canonical design (through fg_design_alias, never raw yard text) and thickness, derives QZ-NAME-THK, and writes absolute values to every sellable quartz Product2 row on every run, undiffed and deliberately so (zero when sold out), and hash-diffed absolute values to one row per stock line in a new ERP_Stock__c object — slabs, every sample shelf, never-cut colours, box and stand counts, and the 30 mm lines flagged "no Salesforce product". Unknown spellings go to an ERP worklist, never to Salesforce. (B) Boxes are counted and stands serialised in four new sampling tables, and they leave stock in the same locked transaction as the pieces. (C) Reps raise requests through the existing screen flow; approval routing already covers New Stand only and is left alone. The ERP pulls by state, resolves lines (the desk builds free-text requests into shelf lines in the ERP, which writes them back as items), checks stock every run, pushes the verdict, and the incharge marks Packed (a real SamplingDispatch, stock leaves) then Sent (Status__c = Dispatched).

## Why this one

Thin-mirror scored highest (40.7) and for the right reasons: it is the smallest thing that ships, it has no inbound surface, every write is an absolute value diffed against a mirror so any run is replayable, and ownership by column means there is nothing to merge. It is kept as the base. Its two real weaknesses — a SystemModstamp watermark that can be wrong after an outage, and Product2 fields plus a separate shelf object as two different search surfaces — are exactly the two things erp-middleware did better, so those are grafted in: pull by state with a per-row dirty flag, and one ERP_Stock__c object that is both the search and the thing a request line points at. Salesforce-pushes lost on realism (seven Apex classes, three LWCs, a public endpoint, in an org whose last integrator shipped a log row and no middleware), but its incharge board, its learned line mapping and its shared releasePackage are the parts that make the loop usable day to day, so they are grafted in too.

Two live facts from the org then removed work rather than added it, and both were checked rather than assumed: approval-only-for-New-Stand already exists (PCES_Stamp_Sample_Requester's Needs_Approval decision, 5 Sept 2026; the submit flow and the approval entry criteria both key off Approver__c; the two requests in the org have no approval instance), so the erp-middleware plan to change entry criteria and add a routing flow would have put two submitters on one record and is dropped; and reps write free text by the org's own design, with the desk building the items — which is what the ERP now is. Every fatal-adjacent flaw a judge named is closed in the text: the approval record lock and queue ownership (Modify All on the request object for the pending window; the Unlock action once planned here was withdrawn 2026-09-16 as unnecessary), sold-out zeroing across all 110 products with sold-out kept apart from retired, no Returned value on Sample_Stand__c, no duplicate stand lookup, the required Account__c carried onto the stand, Inbound/Outbound and the hyphenated touchpoint values, the run lease released on finish, no query string in a cron path, sweepExpiredReservations before counting, the unit rule with three answers and a stand type on the request, lines merged by item id, boxes leaving through the manual dispatch builder, held requests not committing, "10 mm" not folded by canonThickness, validation rules on a custom permission, Product2 record types, the list-view component cap, and an honest RETURNED intake source.

## Grafted from the other two designs

1. erp-middleware: the request pull by STATE (ERP_Request_No__c blank; then every open request re-read by id; then sent requests the rep has closed) and the per-row sf_dirty flag that clears only on a per-record composite success — no watermark, no replay, no dead-letter queue.

2. erp-middleware: one ERP_Stock__c object keyed SLAB|code|FINISH|GRADE / SAMPLE|shelf id / UNIT|type id that is both the rep's stock search and the row a request line looks up, so the automatic check resolves a line by id with no name matching.

3. erp-middleware: the publish rule (a slab line reaches Salesforce only through a canonical in fg_design_alias or a ProductCode match) with sf_stock_unmapped as the visible worklist, and retirement rows instead of deletes.

4. erp-middleware: serialised stands with an append-only ledger, the manageUnits action kept off addStock, and the belt-and-braces approval check in the ERP's own pack rule.

5. salesforce-pushes: the incharge board with Pack and Sent rendered disabled WITH the reason, and the inline map-line picker that writes sf_sample_colour_map so the next request in the same words resolves itself.

6. salesforce-pushes: releasePackage(tx, …) extracted from the dispatch POST so the manual builder and the pack route share one lock order, one planRelease and one decrement — and the unit line on the manual builder that comes with it.

7. salesforce-pushes: the provisioned "Salesforce" system user stamped as the actor when a Salesforce Delivered moves an ERP package, and the principle that a sync failure shows on the record and the card rather than in a function log.

8. salesforce-pushes: the ERP acts only on what it has read from Salesforce itself — in a poll that is the pull, and it is why approval is enforced from Salesforce's own Approval_Status__c rather than anything a layout could forge.

9. thin-mirror (base): one cron route with four phases, sf_stock_mirror hash diffing, ownership by column with the guarded Status__c projection, the never-stocked rows so "never cut" and "none left" differ in Salesforce, the SF_ENABLED kill switch, dry-run, the one-open-run lease, ERP_Other_Thickness_Stock__c on the sibling product, the client-credentials Connected App, and the ship order B → A → C.

## A — inventory in Salesforce

DIRECTION. ERP → Salesforce only. Salesforce never writes stock and never calls the ERP; the product MASTER stays Salesforce's, the STOCK is the ERP's.

TRIGGER AND FREQUENCY. One cron, `{"path":"/api/salesforce/sync","schedule":"*/10 * * * *"}` in vercel.json (the project already runs an hourly cron, so the plan allows sub-daily schedules). The route takes the cron secret exactly as /api/report/slab-intake-digest does — `x-cron-secret` or `Authorization: Bearer <CRON_SECRET>` through secretEqual — and, unlike the digest, ALSO accepts an admin session (commercialGate('admin','settings')), deliberately, so the owner can read the dry run in a browser without a terminal. The secret door refuses everything when CRON_SECRET is unset, but the admin door does not close with it: an admin session reaches `?phase=whoami` and `?phase=stock&dry=1` regardless. Only the LIVE push is secret-only — an admin-authenticated non-dry call answers 200 {ok:false}, on top of the SF_ENABLED check. ANY PHASE ADDED HERE MUST SIT AFTER THAT CHECK; `?phase=whoami` is handled above it only because it reads and never writes. Also — `dynamic = "force-dynamic"`, `maxDuration = 120`, and is added to CRON_ROUTES in src/lib/routeCaps.ts so both edge gates let it through (a cron route left off that list is bounced to /login with a 302 that Vercel logs as success — the digest already paid for that lesson). Four phases in order, each catching its own error so a stock failure cannot stop a request push: pull requests, check stock on open requests, push stock, push request status. `?phase=stock&dry=1` computes and returns without writing. SF_ENABLED unset makes the run answer 200 `{ok:false, reason}` and touch nothing. A misconfiguration — any of SF_LOGIN_URL / SF_CLIENT_ID / SF_CLIENT_SECRET missing — answers 500, as does a phase that throws, so the Vercel cron log is red; this was 200 until 2026-09-17, which meant a sync that had never once worked logged green. An unknown `?phase=` answers 400. The SF_ENABLED refusal above stays 200 on purpose: it is a deliberate state, not a fault. Two more triggers hit the same module: an admin "Run now" button on /office/salesforce, and a best-effort `after()` call (the pattern /api/telegram/webhook uses) at the end of every pack and send so the numbers a rep sees reflect the pieces that just left. ONE RUN AT A TIME: sf_sync_run has a partial unique index `((1)) WHERE finished_at IS NULL`; a second invocation answers 200 "already running"; a run open longer than 10 minutes is closed by the next run with ok = false and finished_at set, releasing the lease, before it inserts its own row (there is no ABANDONED status column — sf_sync_run records ok as a nullable boolean); the lease is released when the run finishes, not by expiry, so "Run now" works the moment a cron completes.

WHAT IS COUNTED (slabs). `sweepExpiredReservations()` first, as searchAvailable does, so a lapsed 5-day hold counts as available. Then one raw query, not 19,538 rows: `SELECT design, slab_thickness, COUNT(*)::int FROM fg_finished_slab WHERE status = 'AVAILABLE' AND slab_mark = 'FULL_SLAB' GROUP BY 1, 2` — a few hundred groups — and the same grouped count restricted to `slab_number = ANY(<unapproved set>)`, subtracted. The unapproved set is getUnapprovedSlabNumbers(true): STRICT, so a failure to read the sales-approval list throws and the run fails closed rather than publishing stock the sales screens hide (owner question 2). CTS/SAMPLE-marked slabs are excluded for the reason searchAvailable excludes them: dispatch would refuse them. The raw AVAILABLE total (19,538 today) is logged beside the filtered one every run so the gap is visible.

HOW A ROW BECOMES A SALESFORCE LINE. The alias table (287 rows) is read once per run into a Map exactly as inventory-bridge.aliasMap() does and for the same reason — never memoised across runs, because designs get merged while the app runs. canonical = map.get(design) ?? design. mm = canonThickness(slab_thickness) → '1.2 cm' 12 · '2 cm' 20 · '3 cm' 30 · '7 mm' 7; anything canonThickness passes through unchanged — "3 cm to 2 cm" (440 slabs), "2cm to 12mm", and "10 mm" (25 slabs; canonThickness does NOT fold it, it reads as 1.0 cm and falls through) — is THICKNESS-unmapped and never counted against a product. code = `QZ-${canonical.toUpperCase().replace(/[^A-Z0-9]/g,'')}-${mm}`, the scheme DISCOVERY §1 proved deterministic. THE PUBLISH RULE, and it is the answer to the 383 noisy names: a (canonical, mm) line is published only when the canonical is KNOWN — it appears as a `canonical` value in fg_design_alias, OR its derived code at ANY thickness matches an active Quartz Slab Product2.ProductCode. Everything else ("Alabester White", "Astal Mist", "Artermis", trials, variants) is reported unmapped with its AVAILABLE count and reason (UNKNOWN_DESIGN or THICKNESS) — NOT to a table: sf_stock_unmapped was never built, and the spellings come back in the run summary only, so they do not outlive the response (see §7), listed by count on /office/salesforce and as a badge on the finished-goods alias screen — the alias job DISCOVERY says exists regardless, now worked by stock value. Aliasing "Astal Mist" → "Astral Mist" folds its count into QZ-ASTRALMIST-20 on the next run with no Salesforce change. Deriving a code from raw yard text is refused in stock-rules.ts, not by convention, and tests/salesforceStock.test.ts runs the twelve DISCOVERY §3 fixtures, the "Astal Mist" refusal, the "3 cm to 2 cm" and "10 mm" thickness cases and the 30 mm sibling case.

WHAT IS WRITTEN — Product2. One SOQL per run: `SELECT Id, Name, ProductCode, ERP_SKU__c FROM Product2 WHERE IsActive = true AND Family = 'Quartz Slab'` (110). Match key ERP_SKU__c when filled, else ProductCode (identical by DISCOVERY); where ERP_SKU__c is blank the job writes ERP_SKU__c = ProductCode in the same PATCH, so the other 55 fill on run one. EVERY one of the 110 gets a payload every run (the judges' sold-out fix): ERP_Available_Slabs__c (0 when the ERP holds nothing at that thickness — a sold-out product reads 0, never last week's number), ERP_Match__c (Matched · Not at this thickness · No ERP design — a picklist whose values are assigned to the Quartz Slab record type, since Product2 has five record types), ERP_Other_Thickness_Stock__c ("30 mm: 118" — stock of the same canonical at thicknesses with no product), ERP_Stock_As_Of__c (the run time). ERP_In_Stock__c is a formula (ERP_Available_Slabs__c > 0) so in/out cannot drift from the count. EVERY SELLABLE PRODUCT IS PATCHED EVERY NON-DRY RUN, UNDIFFED — `PATCH /services/data/v<ver>/composite/sobjects` allOrNone:false, 200 per call (110 fits in one), so the diff would save nothing and the unconditional write IS the sold-out fix: a product the ERP has no stock for still receives its zero. Hash diffing governs the ERP_Stock__c rows ALONE, through sf_stock_mirror (sf_key PRIMARY KEY — the ERP_Key__c — payload_hash, pushed_at, push_error); there is no target column, so a Product2 row cannot be mirrored even in principle. There is no periodic full push and no sf_sync_state.last_full_push_at: forcing a full re-push of the stock rows means clearing sf_stock_mirror, not setting a flag or a query string. NEVER CLEAR IT WHILE BOTH SLAB KEY SHAPES ARE LIVE: every decision about an old-shape row is made from the mirror (planTransition reads which shape it holds and what Salesforce accepted), so a cleared mirror forgets the old rows exist — they are never retired, and any that were carrying a remainder keep that count for good. THE SWITCH-OVER IS FINISHED when the mirror holds no two-segment SLAB key: `SELECT count(*) FROM sf_stock_mirror WHERE sf_key ~ '^SLAB\|[^|]+$'` returns 0, or a dry run shows shapeMigration.oldShapeRows 0. That can take a while by design — a product sold out at the switch keeps its old row until it is restocked. If the mirror is lost before then, the old keys have to be recovered from Salesforce itself (SOQL `SELECT ERP_Key__c FROM ERP_Stock__c WHERE Kind__c = 'Slab' AND Retired__c = false`, re-seeded into sf_stock_mirror with any payload_hash) or retired by hand; the ERP never reads ERP_Key__c back on its own.

WHAT IS WRITTEN — ERP_Stock__c, the search object. One custom object, one row per stock line, upserted by external id ERP_Key__c through `PATCH …/composite/sobjects/ERP_Stock__c/ERP_Key__c` (200 per call, allOrNone:false; ~500 rows today, three calls, diffed through the same mirror). Keys and kinds: `SLAB|QZ-ARVAWHITE-20|POLISHED|A` (Kind Slab, ONE ROW PER FINISH AND GRADE since 2026-09-23 — polish and grade are per slab, so one design and thickness holds several at once; Salesforce's REPLY-10 option (b), our REPLY-16. Finish and grade segments uppercase, `_` for spaces, `/` for a typed `|`, `-` for none; never over 80 characters — an over-long segment becomes its first seven characters, `~`, and an FNV hash of the whole value. BEHIND A SWITCH, SF_SLAB_SPLIT: unset, the rows are written byte-for-byte as the two-segment `SLAB|<code>` rows they were, so deploying is not migrating; `?dry=1&split=1` previews it against production. Once set, THE OLD ROW CARRIES EXACTLY THE SLABS SALESFORCE DOES NOT YET HOLD A REPLACEMENT ROW FOR (planTransition): retired once every replacement for its code is accepted (in the same run, in a second write after the first is answered); while some are refused it stays live as the full legacy row (name, design, product all current) with the sum of the refused slices as its count, so totals are exact and nothing disappears; while all are refused it IS the pre-switch row, byte for byte, so a refusal costs no extra write and changes nothing a rep sees; a code with no replacement at all (sold out at the switch, or merged away) goes through the ordinary diff. Switching back holds the several split rows untouched until the full legacy row is VERIFIED — accepted this run, or mirrored with exactly this run's payload — because the legacy key may be in the mirror holding only a forward-direction remainder (verifiedKeys). Until any row of the current shape has ever been accepted, only the first 200 new rows go out, and the rest only if one of those is accepted (probeWave), so a blanket refusal costs one call a run rather than the daily budget; once any row of the shape has been accepted the brake is off, and a row refused on its own is re-sent every run like any refused row. WRITES GO OUT ONE CHUNK AT A TIME (sendChunks), each recorded in the mirror as Salesforce answers it — compositePatch alone throws on the first bad chunk and loses the answers to the ones already committed, and a committed row the mirror never learned of, sold out before the next run, was never touched again: a phantom. A 400 on a chunk (a field hidden from the integration user is refused per REQUEST, not per row) refuses that chunk's rows and the run carries on; rows carrying Grade__c go in chunks of their own (partitionByNewField), so such a refusal costs only them. Any other error stops the run, and a run that stops is now recorded in sf_sync_run with its calls, so callsSpentToday counts it. KNOWN WINDOWS, where the OLD row keeps its previous count while the split rows beside it have moved on — so a design's total reads high if the old row should have shrunk, low if it should have grown: (1) a run that stops before its old-row write; (2) a REFUSED old-row write (retirement or remainder). Both are put right by the next run whose old-row write succeeds — ten minutes when nothing else is wrong, longer through a stand-down (orgNearlyOut, overOwnBudget) or a refusal that repeats. Old-row refusals are named in wrote.failures by key, ahead of the capped list of other refusals. The one phantom left: a chunk Salesforce committed whose answer never reached us (the connection dropping mid-response), if a row in it then sells out before any run re-sends it. Product__c = the Product2 Id when the code matched, Design__c (the code's commonest spelling, not whichever group Postgres returned first), Thickness_mm__c, Finish__c (canonicalFinish — the owner's four words, as the sample rows send — else the yard's own text), Grade__c (canonicalGrade: "Not graded yet" blank, "C (Reject)" C, otherwise as QC wrote it), Series__c (colour chart: the design's own chart entry first, and only if the chart does not list it, the alias spellings mapped onto it — the first production dry run found "Ultima White" aliased to "Brilliant White" while the chart puts the two in different series, which had sent Brilliant White blank; blank for the many designs not on the chart), Available_Qty__c; Product2.ERP_Available_Slabs__c stays the sum over every row of the code); `SAMPLE|<sampling_stock.id>` (Kind Sample; Series__c, Colour__c, Finish__c, Size_Label__c from sampleSizeLabel, ERP_Colour_Finish_Id__c, ERP_Size_Id__c; INCLUDING shelves at zero — a shelf that emptied is "none left"); `FINISH|<product_colour_finish.id>` (Kind Sample, Never_Stocked__c true, no size — the colour+finish rows /api/sampling/inventory returns with sizeId null, so "never cut" stays a different answer from "none left" in Salesforce as it is in the ERP); `UNIT|<sampling_unit_type.id>` (Kind Box or Stand, Available_Qty__c = on hand, Part B). Name is what a rep searches: "Arva White 20 mm · Polished · Grade A" (a row with neither value keeps "Arva White 20 mm"), "Cappuccino (Polished) 4 × 4 in · 20 mm", "Floor Stand". In_Stock__c and Stale__c ((NOW() − Synced_At__c) > 1/24) are formulas; Synced_At__c is stamped on every row every time it is written. RETIREMENT VERSUS SOLD OUT, kept apart deliberately: the slab line set each run is the aggregate UNION every mirror key whose product CODE still resolves (still has stock, or still matches a product — read out of either key shape by slabKeyCode) — those absent from the aggregate are written with Available_Qty__c 0 and Retired__c false (sold out); a mirror key whose canonical no longer resolves (merged away by an alias edit) or a shelf row that no longer exists is pushed once with 0 and Retired__c true, then dropped from the mirror. Nothing in Salesforce is ever deleted by the ERP; a request line that pointed at a retired row still resolves.

HOW THE REP SEARCHES BOTH. A tab "ERP Stock" on ERP_Stock__c with four list views — Slabs in stock (Kind = Slab, In_Stock__c, Retired__c = false), Samples in stock (Kind = Sample), Stands & boxes (Kind IN Box, Stand), Everything incl. unmapped — the standard list-view search box, and global search, all matching Name. That is the owner's "stock search should have both slab and sample option": one screen, one toggle by list view, and the same rows the request line points at (Part C). The product-centric view reps already use gets the four Product2 fields on the Quartz Slab layout and a list view "Quartz — in stock". An App Builder page holding both list views is optional; the list-view component caps rows, so the object tab and global search are the real search.

THE 30 mm STOCK (10,391 AVAILABLE slabs; 59 designs / 4,202 slabs where Salesforce sells the design at 20 or 12 only). Never hidden, never mis-attributed, never rolled into a 20 mm number. Every 30 mm line whose design is known passes the publish rule and is written as an ERP_Stock__c Slab row ("Arva White 30 mm", Product__c null, Product_Missing__c true) — searchable and filterable on In Stock from day one; the sibling product's ERP_Other_Thickness_Stock__c reads "30 mm: N"; /office/salesforce lists the 59 codes (QZ-ARVAWHITE-30, …) with counts and offers a CSV. DEFAULT (owner question 1): the ERP does not create products — a product implies a price-book entry the ERP knows nothing about — the admin creates them from that CSV with Data Loader (Family Quartz Slab, IsActive as he decides, ERP_SKU__c = ProductCode), and the next run links them by code with no code change. Alternative on request: SF_CREATE_MISSING_PRODUCTS=1 and the run inserts them once, unpriced.

RUN RECORD. One Integration_Log__c row per run — Touchpoint__c 'T3 - Inventory lookup' (the value as it exists, hyphen not en-dash), Direction__c 'Inbound' (the two values are Inbound/Outbound), Object_Type__c 'ERP_Stock__c', Status__c Success/Failed, Payload__c the summary JSON (matched 75 / not-at-thickness 10 / no-design 35 / unmatched spellings with counts / unclassified thicknesses / 3 cm without product / shelves written / requests pulled, checked, pushed / duration), Error__c on failure — and the same summary in sf_sync_run. API budget: ~144 runs a day at 4–6 calls each, under 1,000 calls, with Sforce-Limit-Info read off every response and shown on the admin page; the stock phase skips itself and logs why if under 10% remains.

## B — boxes and stands in the sampling module

WHAT THEY ARE IN THE ERP TODAY: nothing (DISCOVERY §2). Salesforce already treats both as trackable units — Sample_Stand__c.Stand_Type__c is Floor Stand · Wall Display · Counter Display · Sample Kit Box · Other with Serial_No__c, a REQUIRED Account__c, Installed_Date__c, Last_Refreshed__c, Location_Note__c, and Status__c Requested · Dispatched · Installed · Needs Refresh · Retired — so the ERP model mirrors those words rather than inventing its own.

DATA MODEL (scripts/0086-sampling-units.sql — allocated 0084 when this was written on 2026-09-14, but 0084 and 0085 were taken the next day by the unrelated proforma work (0084-pi-salesperson, 0085-pi-seller), so boxes and stands shipped as 0086, the Salesforce sync state as 0087, and the request loop becomes 0088 — additive and idempotent, applied with `npx prisma db execute --schema prisma/schema.prisma --file …` then `npx prisma generate`, never db push; Prisma models hand-added under the SAMPLING banner, marked NOT touched by gen-schema.py):
• `sampling_unit_type` — id, kind (enum sampling_unit_kind BOX | STAND), name, sf_stand_type (the exact Stand_Type__c value it mirrors to), serialised boolean (default true for STAND, false for BOX), capacity_pieces int null, min_qty int default 2, active, position. Seeded ON CONFLICT DO NOTHING with the four Salesforce types: Sample Kit Box (BOX, counted), Floor Stand, Wall Display, Counter Display (STAND, serialised). "Other" is not seeded; an admin adds a type when one exists.
• `sampling_unit_stock` — unit_type_id UNIQUE, quantity int with CHECK (quantity >= 0). The running count for counted types; the same shape as sampling_stock: the quantity moves, the row does not.
• `sampling_unit_serial` — id, unit_type_id, serial_no text UNIQUE (the number stencilled on the stand; the ERP proposes <TYPE>-<seq>, the incharge may overtype), status (enum sampling_unit_serial_status IN_STOCK | RELEASED | DISPATCHED | INSTALLED | RETURNED | RETIRED), customer_name, sales_request_id null, dispatch_id null, sf_stand_id null (the Sample_Stand__c Id once pushed), installed_at, location_note, created_by_id (users.id, no hard FK — the Sales/Chromia precedent), timestamps; index (unit_type_id, status). On hand for a serialised type is `count(*) WHERE status = 'IN_STOCK'`, computed, never stored twice.
• `sampling_unit_ledger` — append-only like sampling_intake: id, unit_type_id, serial_id null, delta int, reason (enum INTAKE | RELEASE | RETURN | ADJUST | RETIRE), reference text (a request number, a supplier note), sales_request_id null, dispatch_id null, note, created_by_id, created_at; index (unit_type_id, created_at). Every change to a count or a serial writes one ledger row in the same transaction, and the admin page asserts quantity = Σ delta per counted type and shows any drift.
• `sampling_dispatch` gains `unit_type_id`, `unit_serial_id`, `sales_request_id` (all nullable text, indexed; no hard FK per the module's precedent), so a package knows what it was packed in and which Salesforce request it fulfilled.
• `sampling_intake_source` gains the value RETURNED (ALTER TYPE … ADD VALUE), so pieces that come back from a cancelled-after-pack request can be re-intaken with source_ref = the request number instead of faking SAMPLE_CUTTING (a judge caught that the enum has no honest value today).

HOW STOCK IS COUNTED. On hand = sampling_unit_stock.quantity (counted) or the IN_STOCK serial count (serialised). Committed = units needed by OPEN sales requests whose verdict is AVAILABLE and that are older than the one being checked — a held or short request does not commit (a judge showed one oversized request would otherwise starve every later one). Available = on hand − committed. UNITS LEAVE AT PACKED, in the same transaction as the pieces, through the one shared function: `releasePackage(tx, { customerName, destination, reference, notes, lines, unit?, releasedById })` in src/lib/sampling/release.ts, extracted from the body of today's POST /api/sampling/dispatch — the shelf locks in sorted (sizeId, colourFinishId) order, then the unit row or the chosen serial locked LAST so a unit lock can never deadlock a shelf lock, re-read, planRelease all-or-nothing on the pieces and the pure `checkUnitRelease(onHand, qty)` (same shape as lifecycle.checkRelease) on the unit, then decrement / IN_STOCK → RELEASED, create the SamplingDispatch, write the ledger row. The existing dispatch route calls it too and gains an optional "Packed in" picker (type, and the serial for a stand), so a walk-in package consumes a box as well — without that the box count drifts within a week. RELEASED → DISPATCHED at Sent; INSTALLED / RETURNED from Salesforce (Part C step 9); a RETURNED serial goes back IN_STOCK or to RETIRED only by the incharge's hand on the units screen, never automatically — a return is a question about condition that a person answers, the same reason the sample lifecycle has no undo.

WHICH REQUEST CONSUMES WHAT (the pure `unitNeeded(dispatchType, standTypeRequested)` in src/lib/sampling/unit-rules.ts, tested): Sample Kit → one Sample Kit Box; New Stand → one STAND of the variant on the request's new Stand_Type_Requested__c (Floor Stand / Wall Display / Counter Display), or, when blank, the variant the incharge picks at pack — never a silent Floor Stand default; Stand Top-up, Loose Samples, Replacement → pieces only, no unit. Three answers, not two: a top-up refills a stand the customer already has (Sample_Dispatch__c.Sample_Stand__c points at it), so it must not decrement a stand or be refused at zero on hand.

WHAT THE SAMPLING INCHARGE SEES. Boxes and stands got their OWN sidebar row — "Boxes & Stands" → /sampling/units in components/Nav.tsx — deliberately NOT a card on /sampling, which is unchanged and still only the shelf tree. On /sampling/units, per type — on hand, committed to open requests, available, red when available < min_qty; a serialised type expands to its serials with status and, when out, the customer and date. /sampling/units: Add stock (type; quantity, or a list of serial numbers for a serialised type; note), Adjust (a count correction — refused without a reason), Return / Retire a serial, and the ledger (date, ±n, reason, request number, serial, who). All writes gate a NEW action `manageUnits: ["SAMPLING","ADMIN"]` in lib/sampling/actions.ts — deliberately not addStock, which admits the fabrication floor for the one errand of putting an offcut on the shelf; a box is not the floor's, and actions.ts documents exactly that trap. On a sales request card each unit line reads "1 Floor Stand needed — 2 available (FS-0007 will be used)" and the pack button is disabled with that sentence when short.

WHAT SALESFORCE SEES. Counts ride in ERP_Stock__c as Kind Box / Stand rows (Part A), so a rep sees "Floor Stand: 3 available" before raising a request that needs his manager. At Sent for a New Stand the ERP upserts Sample_Stand__c by a new external id ERP_Stand_Id__c (= the serial row id, so a retried send updates rather than twins): Stand_Type__c from unit_type.sf_stand_type, Serial_No__c, Status__c 'Dispatched', Account__c from the request's own required Account__c (Sample_Stand__c.Account__c is required — the pull selects it), Location_Note__c = the ship-to text — and sets the request's EXISTING Sample_Stand__c lookup to it; no new lookup on the stand, because Dispatches__r already exists. Installed → Status__c 'Installed', Installed_Date__c. Returned: Sample_Stand__c has no such value, so the ERP writes nothing to the stand's status on a return; the serial is RETURNED in the ERP, and if the incharge retires it the ERP writes 'Retired', a value that exists. Boxes get no Sample_Stand__c record by default (a consumable's record is the request that consumed it; the picklist value is there if the owner wants one later).

## C — the request, from a rep raising it to "sent"

OWNERSHIP, stated once and enforced by which columns each side may write. Salesforce owns: Status__c values Requested · On Hold (when a person set it) · Cancelled · Delivered · Installed · Returned; Approval_Status__c and Approver__c; every request field (type, account, opportunity, needed-by, ship-to, free text, rep-authored items). The ERP writes a Status__c value only when the current value is Requested, or On Hold with an "ERP:" reason, checked live in the same composite call's read-back — never over Cancelled, Delivered or anything a person set. 3. PULL [ERP, phase 1, every run, by state]. Lines are MERGED by sf_item_id, never replaced: a rep-authored item is Salesforce's while the request is OPEN (edits and deletions follow), an ERP-authored item (ERP_Line_Id__c set) is the ERP's, and the incharge's mappings survive a rep edit. A CHECK, NOT A RESERVATION: nothing is decremented (owner question 5).

5. PUSH THE VERDICT [ERP, phase 4, and immediately after any ERP-side change via after()]. ## What goes wrong, and what the design does about it

1. SALESFORCE DOWN, TOKEN REFUSED, OR API LIMIT HIT (expired secret, deactivated integration user, revoked app): the run fails at getToken or the first SOQL, closes its sf_sync_run row with ok = false and the OAuth or API error text (design, not behaviour — nothing writes sf_sync_run yet), answers 500 so the Vercel cron log is red, and changes nothing in the ERP — no watermark to advance, no mirror hash to move. Requests raised in Salesforce simply wait; the board banner reads "Salesforce last read 47 min ago" in amber; Product2's ERP_Stock_As_Of__c and every ERP_Stock__c row's Stale__c go visibly stale rather than silently wrong. Every ERP-side change since the outage sits as sf_dirty and lands in one composite call on the first good run. After three consecutive failures the admin page shows a red banner; the owner may add one line to the existing daily email later — no new alert channel is invented.

2. ERP OR NEON DOWN, OR A BROKEN DEPLOY, for hours or a day: Salesforce keeps accepting requests and approvals; reps see ERP_Status__c blank and no ERP_Synced_At__c, which is the honest state. When the ERP returns, the next run pulls everything with ERP_Request_No__c blank in CreatedDate order, re-reads every open request, checks stock and pushes verdicts. Nothing is replayed by hand because nothing is time-windowed: the pull is by state.

3. A REQUEST FOR A COLOUR THE ERP DOES NOT KNOW — and today EVERY request, because reps write free text ("16 pieces, 7.5", "10 pieces xyz") and add no items: the request is pulled, never dropped; verdict NEEDS_REVIEW; Salesforce shows ERP_Stock_Check__c Needs review with the text quoted and Status__c On Hold "ERP: line 1 — sampling desk will map it"; the card lands in the Needs review column where the incharge builds the lines from the catalogue (on-shelf beside each size) or maps the rep's wording, which is stored in sf_sample_colour_map so the next request in the same words resolves itself; the ERP writes the lines back as Sample_Dispatch_Item__c rows so the rep sees the pack list. A colour that genuinely is not in the 56-colour catalogue stays On Hold with a reason the rep can read ("Nebula Ash was never cut — raise a cutting request"); a catalogue colour is a seed edit, how the module already adds colours; nobody guesses.

4. DOUBLE-SENDS, each closed by construction. Pull: sf_id UNIQUE — a request read twice is an update; lines merge by sf_item_id. Push: every value written is absolute, so writing it twice is the same as once; sf_dirty clears only per record on a success in the composite response, so a push that landed but whose acknowledgement the ERP failed to store is re-sent once with identical values; ERP-authored items upsert by ERP_Line_Id__c; the stand upserts by ERP_Stand_Id__c. Pack: `updateMany WHERE status = 'OPEN'` inside the same transaction as the locked release — a second tap or a second tablet gets 409 "already packed" and nothing moves. Send: checkTransition refuses DISPATCHED → DISPATCHED. Cron overlap: the partial unique index allows one open run; a second invocation exits before touching anything; a run dead for 10 minutes is closed with ok = false and superseded (there is no ABANDONED status — sf_sync_run records a nullable ok boolean).

5. STALE STOCK NUMBERS. A Salesforce number is at most one cadence old and every row says when it was taken; Stale__c flags anything older than an hour, which only happens when the sync has stopped. Staleness cannot over-commit: the ERP re-checks live at pull, on every run while a request is open, on every board load, and finally under FOR UPDATE at pack — a request that read "12 available" in Salesforce and finds 9 at pack time is refused with the shortfall named, exactly as the dispatch POST refuses today. Two reps can both see "3 available"; the older AVAILABLE request commits them in the younger one's check, the first packed wins, and the loser reads Short within a cadence. A pack or send triggers an inline stock push so the next rep sees the pieces that just left.

6. APPROVAL LOCK AND QUEUE OWNERSHIP. The records are owned by the PCES Sampling Desk queue and a Pending New Stand is locked by the approval process (LockType Workitem); an integration user with plain object Edit gets ENTITY_IS_LOCKED and INSUFFICIENT_ACCESS. The permission set therefore carries Modify All on Sample_Dispatch__c, the final actions unlock the record, and the sandbox test walks one Pending stand end to end before go-live. If a write is still refused, the record's sf_push_error names the code on the card and the admin page — nothing is retried into silence.

7. APPROVAL BYPASS. Three independent locks: the existing Salesforce chain (Approver__c stamped for New Stand only → auto-submit → the approval process, all keyed on one field), the ERP's pull which stores Approval_Status__c as Salesforce holds it, and the ERP's pack route which refuses a New Stand unless that stored value is Approved. A layout or FLS edit in Salesforce cannot get a stand out of the ERP's door; and a rep with no Manager on file — the gap the flow description admits — is shown on the card as the reason the stand waits.

8. ALIAS OR CATALOGUE CHANGES AFTER PUBLISHING. Merging "Astal Mist" into "Astral Mist" moves its count into QZ-ASTRALMIST-20 on the next run; a canonical that stops resolving has its key pushed once with 0 and Retired__c true and drops out of the default list views — never deleted, so a request line that pointed at it still resolves. A Product2 the admin deactivates leaves the SOQL; its stock row keeps publishing with Product__c null and Product_Missing__c true, so stock is never hidden by a Salesforce-side edit. A sold-out line stays with 0 and Retired__c false, and its product reads 0, not last week's count.

9. PARTIAL COMPOSITE FAILURES (a validation rule fires on one record; a field the permission set cannot edit): allOrNone:false lands the other records; the failed record's error is stored on its mirror row or request row, its hash is left unequal so it is retried every run, and the run is logged FAILED with the list. A field-level-security mistake shows as N identical push_errors naming the field on the admin page. A request that cannot reach Salesforce says so on its card rather than pretending.

10. SALESFORCE-SIDE AUTOMATION MEETING THE ERP'S WRITES. Every Status__c value the ERP writes ('On Hold', 'Requested', 'Dispatched') already exists, so PCES_Sample_Stamp_Dates, PCES_Sample_Status_Sync and PCES_Log_Sample_Activity behave as they do for a human edit — Dispatch_Date__c stamped, the opportunity mirrored, the Task logged. No new Status__c value is introduced by default, which is why "Packed" lives in ERP_Status__c. Blocked_Reason__c written by the ERP always begins "ERP:" so the ERP can tell its own hold from a person's and lift only its own.

11. A REP EDITS OR CANCELS AFTER THE PULL. While OPEN the ERP re-reads every open request each run, so an edited quantity, an added or deleted rep-authored item, a hand-set hold or a cancellation is honoured within a cadence and stock never moved. After PACKED the items are locked by validation rule, a cancel is refused by validation rule with the desk's name, and if either arrives anyway (an admin) the ERP ignores it and flags the card "Cancelled in Salesforce after packing" — pieces come back through the intake form with source RETURNED and the request number, by hand.

12. THE UNAPPROVED-STOCK FILTER FAILS TO LOAD. getUnapprovedSlabNumbers(true) throws rather than returning an empty set; the stock phase fails closed — no push, a red run — rather than publishing stock the sales-approval screen is hiding. The previous snapshot stays in Salesforce with its timestamps ageing, which is the truthful state.

13. VERCEL TIME BUDGET. The stock phase reads a few hundred aggregated rows, not 19,538 slabs, and pushes at most ~500 records in three composite calls; the request phases handle dozens of rows; measured expectation is seconds against maxDuration 120. Each phase writes its progress before the next starts, so a killed run leaves consistent tables and is closed with ok = false by the next.

14. THE T5 QUEUE KEEPS GROWING. Whatever writes the 'T5 - Sales order' Pending rows keeps writing one per Order with nothing consuming them. This design does not consume them and does not pretend to; the admin page shows the Pending count so the leak stops being invisible, and the stuck-orders note says what to do with the 26.

## The 26 stuck sales-order rows

What to tell him, plainly. Salesforce has 26 rows in Integration_Log__c marked 'T5 - Sales order', Outbound, Pending, one per Order, written between 2026-07-27 and 2026-09-08, each saying a middleware will pick it up and push it to the ERP. No middleware was ever built, so nothing has ever read them. Queried live on 2026-09-14: the 26 rows point at 26 different Order records, and only 2 of those Orders still exist — 00000151 (2026-07-31) and 00000158 (2026-08-19), both Draft, both with a zero total. The other 24 have been deleted from Salesforce; they read as test orders from the build. So this is not 26 live sales orders lost. It is two draft orders nobody has acted on, plus a mechanism that will add one Pending row for every Order created from now on with nothing consuming it — a live leak, and one he probably did not know about.

What this design does about it: nothing to the rows, and it says so. The ERP's /office/salesforce page shows the Pending T5 count read from Salesforce on every run so the leak stops being invisible, and the Integration_Log__c rows the ERP writes (T3 for stock, T8 for sample requests) sit beside them, distinguishable by touchpoint.

Whether this design should absorb T5: no, and the reason is not effort. A Salesforce Order has no object in the ERP it maps onto without a decision from him — the Commercial module's internal sales order (ORD/{fy}/N{seq}, with its own checklist, hold and numbering, whose numbering owner is itself undecided) and the older /sales module are different things, and DISCOVERY's product master shows 35 Salesforce products with no ERP design at all. Pulling T5 into this cron before that mapping is agreed would create commercial orders nobody asked for against products the ERP cannot name. When he wants it, it is the same cron with a fourth pull — by state, exactly like the sample requests — and nothing on the Salesforce side needs to change, because the writer already logs the intent.

The one housekeeping decision that is his: the 24 rows whose Orders no longer exist should be closed by the admin as Failed with Error__c 'Order deleted; no middleware was ever built', so the queue reads truthfully; the 2 live ones stay Pending until T5 is designed. Default if he says nothing: leave all 26 as they are, visible on the ERP's status page.
