# What to run — the 2026-08-25 batch

Everything changed in this batch, in the order it has to be applied, for **local
dev first and then production**. The owner's rule: *"whatever data I say, in
production I need to feed to the DB as well — so make them like in the files and
run the query."* This is that list.

Nothing here is destructive. Every script is idempotent and safe to re-run, and
the seeder is an upsert keyed on natural names.

---

## 0. The error you are seeing right now

```
Unknown argument `kind`. Did you mean `id`?
```

That is **not** a missing column — it is a stale Prisma client. `kind` is
declared in `schema.prisma` but the client in `node_modules` was generated
before it existed, so it does not know the field is there. It is fixed by step 3
below, and by nothing else.

---

## 1. Apply the SQL, in order

Each one adds columns or renames stored values. They must run in sequence —
`0059` assumes `0058` has run, and so on back.

```bash
npx prisma db execute --schema prisma/schema.prisma --file scripts/0056-polish-qc-grade-before-cts.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0057-polish-qc-slab-mark.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0058-sampling-finish-vocabulary.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0059-sample-orders.sql
```

| Script | What it does |
|---|---|
| `0056` | `polish_qc.quality_grade_before_cts` — keeps the A/B/C verdict that fabrication used to destroy |
| `0057` | `polish_qc.slab_mark` — FULL_SLAB / CTS / SAMPLE, and backfills CTS from the existing grade |
| `0058` | Renames finishes: `Leather → Leathered`, `Honed → Matte`, folding any colour holding both |
| `0059` | `fab_project.kind`, `fab_requirement.colour_finish_id` + `sampling_size_id`, `fab_piece.sampling_intake_id` |

If you applied `0056`/`0057` earlier, re-running them changes nothing.

## 2. Check they landed

```sql
-- 0057: every slab has a mark, and cut ones say so
SELECT slab_mark, count(*) FROM polish_qc GROUP BY slab_mark;

-- 0058: only the four words, nothing else
SELECT DISTINCT finish FROM product_colour_finish
WHERE finish NOT IN ('Polished','Suede','Matte','Leathered');   -- must be 0 rows

-- 0059: the columns exist
SELECT kind FROM fab_project LIMIT 1;
```

## 3. Regenerate the client — this is what fixes the 500

```bash
npx prisma generate
```

Then restart `npm run dev`. Next.js caches the client, so the old one survives a
hot reload.

**Do not run `npx prisma db push`** unless you have read what it will drop. It
removes any column the schema does not declare — that is how `alt_role` and
`alt_branch` were lost. Every column added in this batch IS declared, so a push
is survivable now, but `db execute` is what these scripts are for.

---

## 4. Feed the catalogue

```bash
npm run db:seed:catalogue
```

This is **master data, not test data** — it is meant to run against production,
and it has no environment guard for that reason. It writes:

- 7 series
- 129 colours
- **129 × 4 = 516 colour+finish rows** — every colour in Polished, Suede, Matte
  and Leathered

That last line is the change. It used to write only the finishes the printed
chart listed — three non-default rows out of 132 lines — which is why Carrara
Royale offered "Polished" and nothing else. The chart printed the variants
somebody had photographed, not the finishes the shop can cut.

It is an upsert keyed on series name, colour name, and colour+finish, so
re-running it changes nothing and never duplicates. It is also **corrective**: a
colour re-classified by hand in the database moves back to the series the chart
says.

It aborts before writing anything if the chart has become self-contradictory —
the same colour name under two series would otherwise fail halfway and leave a
production catalogue half-written.

---

## 5. Order matters between 4 and the rest

Run the seeder **after** `0058`. The seeder writes `Leathered` and `Matte`; if it
runs first, `0058` then has nothing to rename and the old `Leather` / `Honed`
rows created by an earlier seed are still there — two spellings, two shelves,
one physical finish.

## The whole thing, in order

```bash
npx prisma db execute --schema prisma/schema.prisma --file scripts/0056-polish-qc-grade-before-cts.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0057-polish-qc-slab-mark.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0058-sampling-finish-vocabulary.sql
npx prisma db execute --schema prisma/schema.prisma --file scripts/0059-sample-orders.sql
npx prisma generate
npm run db:seed:catalogue
```

For **production**, the same six lines with `DATABASE_URL` pointed at Neon.
Take a snapshot first — Neon branches are cheap and none of this is reversible
by re-running it backwards.
